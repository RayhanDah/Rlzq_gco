## 2. Techniques — (1) apport, (2) hyperparamètres rapportés, (3) adaptation RL-GCO

Contexte cible : Rocket League 1v1, physique 120 Hz, tick-skip 8 → 15 décisions/s, **T_RL = 0,0667 s** ; match 5 min ≈ **4 500 décisions** [dérivé] ; obs RLGym 100–230 dims ; ~90 actions discrètes ; reward = ±R au but uniquement ; laptop 14 cœurs/18 threads, 15,4 Go RAM, iGPU Arc, pas de CUDA.

### 2.1 PPO asynchrone + GAE (boucle d'optimisation)
**(1) Apport.** PPO (variante d'actor-critic) + GAE pour réduire la variance ; PPO est le premier algo à avoir montré du progrès (autres PG, Q-learning, ES essayés au début) (§3.2 + note 6). Optimiseurs = pool de GPU qui échantillonnent des minibatchs aléatoires dans un *experience buffer* local, allreduce NCCL2, application synchrone des gradients (§3.2). Le texte ne mentionne **aucun** nombre d'epochs PPO : la réutilisation est pilotée par le ratio production/consommation (sample reuse, §4.4).
**(2) Hyperparamètres.** PPO clip 0,2 ; GAE λ 0,95 ; Adam β1 0,9 / β2 0,999 (Tab. 2) ; Adam ε **non trouvé** ; truncated BPTT sur 16 timesteps (§3.2) ; clipping de gradient **par paramètre** dans ±5√v, v = estimation courante du second moment du gradient non clippé (§3.2) ; buffer de 4 096 samples par optimiseur (App. M.3) ; normalisation des avantages : **non trouvé**.
**(3) RL-GCO.** PPO synchrone classique (collecte → K epochs → collecte) sur CPU : staleness = 0 par construction. Option "double buffer" (collecte du batch N+1 avec la version N pendant l'update) = staleness 1, acceptable (cf. 2.3). Clip 0,2 (aussi le meilleur en PPO Tab. 1, cf. §5). Clipping : implémenter le clip élément-par-élément `|g| ≤ 5·sqrt(exp_avg_sq)` à partir de l'état Adam, ou à défaut un clip de norme globale [hors papier]. Normaliser les avantages par batch [hors papier] : indispensable en GCO car l'échelle des avantages varie énormément avec la fréquence des buts.

### 2.2 Taille de batch (et critical batch size)
**(1) Apport.** Augmenter le batch accélère le training "jusqu'à des millions d'observations", mais **sous-linéairement** (§4.3, Fig. 5a/21). Rerun (983k ts) ≈ **2,5×** plus rapide que le baseline 123k au seuil TrueSkill 175 ; sans cela ≈5 mois au lieu de 2 (§4.3). Le gain semble croître avec le TrueSkill (TS 175 profite plus que TS 100, Fig. 21), mais résultats "inconclusifs" pour la majeure partie du training (>250) (Fig. 21). LR **non retuné** par batch size (§4.3). Les auteurs espéraient le speedup linéaire prédit par McCandlish et al. [28] ; observations "plus tard" jugées cohérentes avec [28] (App. M.1).
**(2) Hyperparamètres.** Batchs testés : 61k, 123k (baseline), 246k, 492k, 983k, 1 966k frames (Fig. 5a/21) ; runs ≈1 semaine, échelle 8× plus petite que Rerun (Fig. 5) ; doubler le batch = doubler optimiseurs **et** rollouts/forward GPUs (§4.3, M.1). Speedup défini en **versions** (Eq. 2) : versions baseline / versions expérience pour atteindre un TrueSkill donné ; seuils 100/125/150/175 (Fig. 5). Variance run-à-run ≈ 2 TrueSkill (Fig. 20, App. M).
**Point clé d'interprétation [dérivé]** : le speedup est mesuré par itération, à ressources proportionnelles. 8× plus de données par itération pour 2,5× moins d'itérations ⇒ ≈ **3,2× plus d'échantillons consommés** pour le même niveau. Le grand batch achète du *wall-clock* avec du matériel parallèle, pas de l'efficacité par échantillon.
**(3) RL-GCO.** Sur un laptop le débit (SPS) est fixe : le temps ≈ échantillons/SPS + coût des updates. Il faut donc rester **sous** B_crit (régime petit batch, efficace en échantillons) tant que le coût CPU des updates reste faible. Mais la récompense GCO est très bruitée, donc le *noise scale* sera élevé. Proposition : démarrer à 50k–100k steps par itération (100k steps ≈ 1,85 h de jeu ≈ 22 matchs de 5 min [dérivé]), mesurer **B_simple** (McCandlish A.1 : norme du gradient sur micro-batch vs batch accumulé, moyennes exponentielles de |G|² et tr(Σ)), et augmenter le batch (200k–500k) quand B_simple grandit. McCandlish (§3) observe que B_crit augmente d'un ordre de grandeur ou plus pendant le training. Heuristique propre [hors papier] : viser assez d'événements "but" par batch (≥ quelques dizaines) pour que l'avantage porte un signal.

### 2.3 Qualité des données — staleness
**(1) Apport.** Au début du projet, les rollouts envoyaient des épisodes complets : données vieilles de plusieurs heures (milliers de gradient steps), gradients "souvent inutiles ou destructeurs" (§4.4). Staleness = M − N (version optimisée − version génératrice) (§4.4). **+≈8 versions de staleness ⇒ ralentissement significatif** (Fig. 5b), soit seulement quelques minutes d'un run de plusieurs mois (§4.4). Cible finale : staleness 0–1, envoi toutes les ≈30 s de jeu, refresh des paramètres ≈ chaque minute, boucle plus rapide qu'un batch de 32 gradient steps (§4.4). Les auteurs suggèrent d'étudier des méthodes plus robustes à l'off-policy (§4.4).
**(2) Hyperparamètres.** Staleness artificielle via une file sur les rollout workers, longueurs 0 (baseline), 1, 2, 4, 8, 16, 32 (Fig. 5b/22) ; staleness mesurée ≈ longueur de file (Fig. 23) ; boucle normale 1–2 min (App. M.2). Asynchrone (baseline) vs synchrone (staleness 0, reuse max 1) : **≈3× plus rapide en wall-clock** pour atteindre TS 150, performances similaires par itération (Fig. 26).
**(3) RL-GCO.** Synchrone (staleness 0) ou double-buffer (staleness 1) ; **jamais** de file de rollouts ou de workers qui gardent une vieille politique plusieurs itérations. Logger la staleness (version de la politique qui a généré chaque step vs version courante). Fig. 26 justifie de chevaucher collecte et update sur les cœurs CPU (gain wall-clock sans perte par itération) si la staleness reste ≤1. Si un jour staleness >1 : correction off-policy type V-trace (IMPALA, réf. [48]) [hors papier].

### 2.4 Qualité des données — sample reuse
**(1) Apport.** Sample reuse = taux de consommation des optimiseurs / taux de production des rollouts (§4.4, Eq. 13). Réutiliser 2–3 fois ⇒ **≈2× de ralentissement** ; 8 fois ⇒ peut empêcher toute politique compétente (§4.4). Le run à 1/8 des rollouts (reuse ≈6,3) plafonne sous 75 TrueSkill (Fig. 24). Reuse <1 (rollouts doublés) légèrement meilleur après ≈5 000 itérations (App. M.3) : le tirage aléatoire dans le buffer fait qu'à reuse 1, certains samples servent 2 fois et d'autres jamais ; plus de rollouts = aussi moins de corrélation entre samples (App. M.3). Conclusion des auteurs : qualité des données > compute consommé (§4.4) ; ajouter des CPU de rollout est un moyen relativement bon marché d'accélérer (App. M.3).
**(2) Hyperparamètres.** Cible ≈1 dans toutes les expériences (§4.4) ; Five 0,8↔2,7, Rerun 1,0↔1,1 (Tab. 2) ; mesuré 0,57–6,3 en faisant varier rollouts ÷2, ÷4, ÷8 et ×2 (App. M.3, Fig. 25).
**Interprétation [dérivé]** : à optimiseurs constants, diviser les rollouts par 2 et observer ≈2× plus d'itérations signifie que les gradient steps supplémentaires sur données réutilisées n'apportent ≈ rien **par échantillon** à cette échelle (et nuisent au-delà de ~4–8).
**(3) RL-GCO.** En PPO synchrone, reuse ≈ n_epochs. Le papier PPO (petite échelle) utilise 3 epochs (Atari) à 10 (MuJoCo) avec succès, donc la leçon OpenAI ne se transpose pas mécaniquement. Proposition : **n_epochs = 1–2** (max 3), à trancher par une ablation en wall-clock jusqu'à un seuil Elo/TrueSkill fixe, avec suivi du KL approx. et de la clip-fraction. Sur CPU, moins d'epochs libère aussi des cœurs pour la simulation (RocketSim). Prioriser plus d'environnements parallèles (le levier "CPU rollout" bon marché du papier) plutôt que plus d'epochs.

### 2.5 Horizon, γ, crédit à long terme
**(1) Apport.** Horizon défini par H = T/(1−γ), T = 0,133 s (§4.5, Eq. 3). Le papier parle d'horizon, **pas de demi-vie** (half-life ≈ 0,693·H [dérivé]). Reprendre un agent entraîné avec un horizon plus long améliore le win-rate face à l'agent de départ, jusqu'aux plus longs horizons testés (6–12 min), avec des rendements décroissants (§4.5, Fig. 6). Les auteurs en concluent que l'optimisation assigne bien le crédit sur de longues durées. L'expérience part d'un agent **déjà compétent** (les auteurs ne s'attendent pas à de la planification longue chez un agent from scratch, Fig. 6).
**(2) Hyperparamètres.** Base 180 s (γ = 0,9993) ; horizons testés 45 s, 90 s, 180 s, 360 s, 720 s (Fig. 6). Five : 60 s → 840 s ; Rerun : 180 s → 360 s ; baseline ablations 180 s (Tab. 2). Changements progressifs, typiquement linéaires sur 1–3 jours (Tab. 2) / 1–2 jours = plusieurs milliers d'itérations (Fig. 7). Passer de 360 à 840 s n'était finalement pas nécessaire (Rerun a réussi sans) (App. C). **Run sparse : H = 1 h (γ = 0,99996)**, 20× le baseline (Fig. 16). Vérif [dérivé] : 1 − 0,133/180 = 0,99926 ; 1 − 0,133/3600 = 0,99996.
**(3) RL-GCO.** Conversion à 15 Hz [dérivé] : γ = 1 − 0,0667/H → H = 5 s : 0,98667 ; **10 s : 0,99333** (demi-vie ≈6,9 s) ; 15 s : 0,99556 ; **20 s : 0,99667** ; **30 s : 0,99778** ; 60 s : 0,99889. Proposition : H ≈ 10 s au départ (relier tir/arrêt/touche au but dans les ~5–10 s qui précèdent), puis 20–30 s une fois que l'agent marque régulièrement. Ratio [dérivé] : 180 s / 2 700 s de partie Dota = 6,7 % ; 6,7 % de 300 s ≈ 20 s. Montée **progressive** (linéaire sur ≥ quelques centaines d'itérations) et **protocole Fig. 6** : reprendre un checkpoint fixe avec H ∈ {10, 20, 40 s}, mesurer le win-rate contre le checkpoint de départ. Le run sparse Dota a justement choisi un horizon beaucoup plus long : en GCO, ne pas descendre sous ~5 s, sinon les buts deviennent invisibles pour la valeur des états de construction.
**λ temporel [dérivé]** : λ = 0,95 à 7,5 Hz = constante de temps T/(1−λ) = 2,67 s. Pour garder 2,67 s à 15 Hz : **λ ≈ 0,975**. Proposition : λ ∈ [0,95 ; 0,975], défaut 0,97. GAE (réf. 1506.02438) trouve le meilleur λ dans [0,9 ; 0,99] et un λ optimal nettement plus bas que γ optimal.

### 2.6 Récompense : shaping, poids de victoire, team spirit, zero-sum, décroissance temporelle
**(1) Ce que fait le papier.** Objectif réel = gagner, mais ils maximisent une récompense avec des signaux additionnels (morts, ressources…), construite une fois au début du projet puis seulement retouchée (§3.2). Shaping "inspiré du potential-based shaping" [58], sans que ses garanties s'appliquent (App. G). Le but affiché est de simplifier le crédit (App. G).
**(2) Valeurs (Tab. 6, App. G).** Win **5** (Team) ; Hero Death −1 ; Courier Death −2 (Team) ; XP 0,002/pt ; Gold gagné 0,006/pt ; Gold dépensé 0,0006/pt ; Health Changed 2 (fraction de la vie max, valeur santé = (x + 1 − (1−x)⁴)/2, jamais tunée) ; Mana 0,75 ; Killed Hero −0,6 (compense l'or/XP) ; Last Hit −0,16 (total ramené à ≈0,4) ; Deny 0,15 ; Aegis 5 (Team) ; Ancient HP 5 (Team) ; Megas 4 (Team) ; T1 2,25 ; T2 3 ; T3 4,5 ; T4 2,25 ; Shrine 2,25 ; Barracks 6 (bâtiments : 2/3 linéairement avec les PV perdus, 1/3 à la destruction) ; Lane Assign −0,15/s hors de sa lane. Avec team spirit = 1, une récompense "Team" pèse 5× une "Solo" (App. G). (Note : la mise en page PDF des lignes de tours est décalée ; valeurs confirmées par la version HTML.)
- **Zero-sum** : à chaque héros on soustrait la moyenne des récompenses ennemies (App. G ; §3.2).
- **Décroissance temporelle** : tout sauf win/loss est multiplié par 0,6^(T/10 min) (Eq. 11), sinon l'apprentissage se focalise sur la fin de partie qui distribue plus de récompense (App. G).
- **Team spirit τ** : r_i = (1−τ)ρ_i + τ·ρ̄ (Eq. 12). Un τ bas réduit la variance du gradient en début de training (App. G). Ablation (Fig. 29, valeurs testées 0 ; 0,3 ; 0,5 ; 0,75 ; 1,0) : τ = 0 meilleur sous TS 125, puis optimum vers 0,5 aux TS 150–175 ; hypothèse : 1,0 meilleur à terme (App. O.1). Valeurs : 0,3 → 1,0 (Five), 0,3 → 0,8 (Rerun), baseline 0,3 (Tab. 2).
**Ce que dit le papier sur "shaping nécessaire vs win/loss pur"** (crucial pour GCO) :
- §3.2 : affirmation **qualitative** que ces signaux additionnels ont été importants pour réussir le training.
- App. G / Fig. 16 : **ablation à petite échelle avec win/loss seul ("0-1 loss")**, horizon 1 h (γ = 0,99996) vs 180 s pour le baseline, mêmes réglages sinon. Résultat : **TrueSkill 155**, contre ≈100 pour un agent scripté (Fig. 16 ; App. J donne ≈105). L'agent bat l'agent scripté de façon régulière, mais avec une **grosse pénalité d'efficacité en échantillons** (non chiffrée dans le texte ; la courbe va jusqu'à ~35 000 itérations sur l'axe). Qualitativement : moins efficace en début de partie, mais il coordonne mieux les combats de fin de partie. Les auteurs présentent les compromis du sparse comme une piste future. TrueSkill final du baseline shaped dans cette figure : **non trouvé** dans le texte.
- App. Q.2 : mettre 128 paramètres à zéro a donné ≈55 % de win-rate après vs avant alors que la récompense shaped restait ≈ identique. Les auteurs l'expliquent par le fait que l'optimiseur ne "voit" pas cette amélioration. C'est un **désalignement shaped-reward / victoire** documenté.
- §4.1 : le style de jeu est probablement influencé par le shaping (qualitatif).
- App. B, Tab. 1 : les retouches des poids de récompense partielle ne sont pas listées (changements "mineurs").
**(3) RL-GCO.** Tout le Tab. 6, la décroissance 0,6^(T/10min), la pénalité de lane et le zero-sum appliqué aux termes shaped sont **interdits ou sans objet**. Reste compatible : récompense ±R au but, déjà zero-sum en 1v1. Team spirit est **sans effet** en GCO même en 2v2/3v3 : toute la récompense est une récompense d'équipe, donc ρ_i = ρ̄ [dérivé de l'Eq. 12]. Prendre **R = 1** et terminer l'épisode au but (retour borné dans [−1, 1]) ; en cas de timeout, bootstrapper V (troncature, pas terminal) [hors papier]. Le résultat Fig. 16 est le seul **existence proof** du papier pour le sparse : faisable, mais cher en échantillons, et à petite échelle Dota. Il faut donc compenser par les leviers compatibles GCO : distribution d'états initiaux (2.13), horizon assez long (2.5), batch suffisant (2.2), entropie (2.13).

### 2.7 Normalisations et value loss
**(1)/(2).** Observations float (booléens inclus) normalisées par **moyenne et écart-type courants par observation** sur toutes les données vues, puis **clip dans (−5, 5)** (App. E). Récompenses normalisées par une **estimation courante de l'écart-type**, et le poids de la value loss s'applique après normalisation (Tab. 2, note c). Value loss weight : Rerun 1,0 ; Five 0,25↔1,0 ; baseline 1,0 (Tab. 2). Normalisation de la *valeur* (PopArt etc.) : **non trouvé**.
**(3) RL-GCO.** Obs : les obs RLGym sont déjà mises à l'échelle à la main. Ajouter une normalisation courante clip ±5 reste utile ; **figer et exporter les statistiques** avec le modèle pour RLBot v5. Récompense : avec ±1 terminal et 0 ailleurs, l'écart-type courant de la récompense par step est minuscule tant que les buts sont rares. Normaliser par lui gonflerait les cibles de valeur au début, puis l'échelle dériverait quand le taux de buts augmente [raisonnement hors papier]. Proposition : **pas de normalisation de reward** (R = 1, valeur ∈ [−1, 1]). Si on en veut une, la baser sur l'écart-type des **retours actualisés** avec un plancher. Une mise à l'échelle par une constante positive n'est pas du shaping (politique optimale inchangée).

### 2.8 Architecture
**(1)/(2).** Un seul LSTM d'une couche de **4 096 unités** (2 048 → 4 096 par surgery le 26/08/2018, params 43,8 M → 156,7 M, Tab. 1) ; unroll 16 (Tab. 2). La mémoire sert à gérer l'information partielle (fog of war ; §2, et §5 au sujet d'AlphaStar). Cinq répliques à poids identiques, une par héros ; un embedding du héros contrôlé est ajouté en entrée ; une opération "cross-hero pool" fait un max-pool des 25 % premiers du vecteur entre répliques (Fig. 17b, App. H). Traitement des obs en arbre : conv 2 couches pour le spatial, module "Process Set" pour les ensembles non ordonnés (Fig. 17a). **Valeur = autre projection linéaire de l'état LSTM** : réseau et gradients partagés avec la politique (App. H ; §3.2). Têtes d'action : action primaire par projection linéaire sur les actions disponibles ; unité cible par attention (dot product) sur les embeddings d'unités, avec masque appris par action ; offsets X/Y en softmax (Fig. 18). Têtes auxiliaires (victoire, rang de net worth, objectifs) : la win-probability rétropropage avec un très petit poids, les autres en stop_gradient ; labels bootstrappés par segment de 30 s (Eq. 10, App. D). L'action échantillonnée précédente fait partie de l'observation (Tab. 4).
**(3) RL-GCO.** RLGym/RLBot donnent l'état complet (positions, vitesses, boost, pads) : la raison principale du LSTM disparaît. Proposition : **MLP** (ex. 3–4 couches × 256–512) [hors papier], avec dernière action dans l'obs comme dans OpenAI Five. Pas de BPTT, donc un coût CPU bien plus faible. Valeur : OpenAI partage le tronc. En GCO, la value loss domine les gradients et son échelle varie avec la fréquence des buts, donc je recommande un **critique séparé** (MLP, bon marché sur CPU) [raisonnement hors papier, à ablater]. Symétrie 1v1 : une seule politique jouant les deux côtés, obs exprimées dans le repère du joueur (miroir bleu/orange) [hors papier]. Tête auxiliaire "qui marque le prochain but" en stop-gradient = **diagnostic** (calibration de V). L'utiliser comme perte d'apprentissage est une zone grise GCO : ce n'est pas une récompense, mais c'est un signal supplémentaire, à valider par le studio.

### 2.9 Fréquence de décision, réaction, espace d'actions
**(1)/(2).** Frameskip 4 (Tab. 2, App. L) ; paramètre "delay" 0–3 pour agir à une frame précise du frameskip : **non appris**, agir au début du frameskip était meilleur (App. L). Action à T+1 calculée sur l'obs de T (asynchronisme pour le débit) → réaction 5–8 frames (167–267 ms) (App. L, Fig. 19). Actions primaires disponibles en moyenne 8,1 contre OG ; filtres d'actions (masques de validité) ; gradients des paramètres ignorés masqués car "pur bruit" (App. F). Tête séparée pour le "teleport", rare, sinon son signal est noyé (App. F). Espace factorisé max 30×4×189×81 = 1 837 080 (App. F).
**(3) RL-GCO.** Tick-skip 8 fixe (15 Hz), sans paramètre de timing sub-tick (cf. "delay" non appris). Table de ~90 actions : masquer seulement l'invalide évident [hors papier]. Attention aux actions **rares mais critiques** (flips/dodges, aerials) : App. F.1 rapporte que l'agent peut vite apprendre à ne jamais prendre une nouvelle action et ne plus l'explorer → surveiller les fréquences d'action par catégorie. Un délai d'1 décision (67 ms) entre obs et action en RLBot est raisonnable ; s'il existe au déploiement, il faut l'avoir aussi à l'entraînement [hors papier].

### 2.10 Self-play et gestionnaire d'adversaires
**(1) Apport.** 80 % des parties contre la dernière version, 20 % contre des versions passées (§3.2, App. N, Tab. 2). Les parties contre le passé évitent le **strategy collapse**, où l'agent ne sait plus jouer que la stratégie étroite qui bat sa version précédente (App. N, renvoi à Balduzzi et al. [60] pour les cycles).
**(2) Algorithme (App. N, Eq. 14).** Chaque adversaire passé i = 1..N a un score de qualité q_i ; tirage p_i ∝ e^{q_i} (softmax). **Tous les 10 itérations**, l'agent courant entre dans le pool avec q = max des qualités existantes. Après chaque partie : si l'adversaire passé gagne → aucune mise à jour ; si l'agent courant gagne → q_i ← q_i − η/(N·p_i), **η = 0,01** (Tab. 2 "Past Opponents Learning Rate"). Fig. 27 : une chute raide de la distribution signale des contre-stratégies qui éliminent les anciens ; plus tard, la distribution s'étale, signe que la progression ralentit. Taille max du pool / élagage : **non trouvé**. Utilisation des données des deux camps en self-play : **non trouvé** explicitement. Aucune expérience quantitative sur le collapse (qualitatif).
**(3) RL-GCO.** Implémentation directe : 80/20 ; snapshot toutes les 10 itérations PPO (ou toutes les 10–25 si les itérations sont courtes) ; q_init = max ; η = 0,01 ; la division par N·p_i compense le fait que les adversaires souvent tirés seraient sinon pénalisés plus souvent [mon interprétation]. Résultat d'une partie = premier but (épisodes terminés au but) ; timeout/nul → pas de mise à jour [hors papier]. Plafonner le pool (ex. 200–500 snapshots, évincer le q le plus bas) pour la RAM [hors papier]. Contre la version courante, entraîner sur les deux joueurs (2× données) ; contre un passé, seul le camp courant génère des données d'entraînement [hors papier]. Bansal et al. (1710.03748) confirment qu'échantillonner d'anciens adversaires stabilise, et que s'entraîner uniquement contre le plus récent est le pire choix (Tab. 1).

### 2.11 Évaluation : TrueSkill
**(1)/(2).** Pool fixe de **83 agents de référence**, de 0 (aléatoire) à 254 (la version qui a battu OG) ; μ alignés pour que l'agent aléatoire ait μ = 0 ; agent scripté ≈105 (App. J). Paramètres : **σ = 25/3, β = σ/2, τ = 0,0, draw_probability = 0,02** (App. J). Des machines dédiées téléchargent en continu la dernière version. Elles ne jouent que contre des références à ≤10 TrueSkill (≈ win-rate entre 15 % et 85 %), traitent la note de la référence comme constante, loggent après **750 parties**, et initialisent la version suivante au μ final de la précédente → une mise à jour ≈ **toutes les 2 h** (App. J). Repère : ≈**8,3 TrueSkill ≈ 80 % de win-rate** (§4.1, Fig. 3). Variation run-à-run ≈2 TS (Fig. 20) ; l'incertitude sur les speedups combine numérateur et dénominateur en quadrature (App. M). Biais : inflation des agents récents évalués sur le code sur lequel ils ont été entraînés (App. J ; Fig. 3 biaisée contre les anciens modèles). Final Five = 254 (Fig. 4) ; Rerun >98 % contre Five final (§4.2).
**(3) RL-GCO.** Même paramétrage TrueSkill (lib Python `trueskill` [hors papier]). Références : aléatoire (ancre 0), 1–3 bots scriptés simples (ex. "fonce vers la balle"/ATBA, plus un défenseur basique) [hors papier], puis des checkpoints gelés de notre historique, ajoutés à mesure que l'agent les dépasse. Gel du pool pour les comparaisons d'un rapport. Fenêtre ±10 TS. 750 parties est trop coûteux sur laptop : viser 100–300 épisodes "premier but" par évaluation, toutes les K itérations, sur 1–2 workers dédiés [hors papier]. Ré-évaluer tout le pool si obs/action/tick-skip changent (inflation App. J). Logger aussi le taux de buts marqués/encaissés par minute contre références fixes : c'est la métrique "native" GCO.

### 2.12 Surgery (continuation Net2Net) et Rerun
**(1) Apport.** Transformations hors ligne qui préservent la fonction (Eq. 1 : π̂(o) = π(o) ∀o ; cas particulier de Net2Net [23]) lors des changements d'obs, d'architecture, d'actions ou d'environnement (§3.3, App. B). Elles ont permis de suivre les patches Dota (passage à 7.21d huit jours avant OG) (§3.3) et d'avoir toujours un agent fort sous la main pour itérer (§4.2).
**(2) Recettes (App. B).**
- Élargir une couche FC : nouvelles lignes de W1/B1 aléatoires, nouvelles colonnes de W2 **à zéro** (Eq. 6) → sortie identique ; ne mettre à zéro que le minimum (sinon symétries).
- LSTM 2048→4096 : impossible de séparer proprement à cause de la récurrence ; nouveaux poids aléatoires **petits**, à l'échelle maximale qui ne fait pas baisser le TrueSkill de façon notable.
- Nouvelles observations : vue encodeur E puis politique, condition π̂(Ê(s)) = π(E(s)) (Eq. 8) ; poids des nouvelles entrées **à zéro** (Eq. 9).
- Changement d'env/actions : souvent stable sur les rollouts ; sinon **annealing 0 % → 100 % des parties** ; si le TrueSkill baisse pendant l'anneal → revert et anneal plus lent. Exemple : Buyback donné sans anneal → l'agent l'utilise mal au début, adapte toute sa stratégie et perd du niveau.
- Suppression : impossible sous équivalence exacte → observations dépréciées gardées à valeur constante (note f de Tab. 4).
- Redémarrage : **LR = 0 pendant "plusieurs heures"** après la surgery (moments d'Adam, régime stationnaire des rollouts) ; **convertir aussi tout le pool d'adversaires passés** ; sinon ces agents gelés jouent moins bien pour toujours.
- Bilan : naïvement, sans surgery le projet aurait pris 40 mois au lieu de 10 (§4.2). Rerun, from scratch avec l'env final : **≈20 % des ressources**, 2 mois, >98 % contre Five ; la surgery a plafonné **plus bas** que le from-scratch (§4.2). Les auteurs jugent la surgery peu utile quand l'environnement est connu dès le départ (§4.2).
**(3) RL-GCO.** La physique RL ne change pas (pas de patchs), donc le cas d'usage principal disparaît. Leçon Rerun : **figer tôt obs/actions/tick-skip/γ** via des runs courts, puis faire **un run propre from scratch**. Surgery seulement pour l'inévitable (ex. ajouter des features d'obs : poids à zéro ; élargir le MLP : Eq. 6), avec LR = 0 pendant 1–3 itérations pour réchauffer Adam et les stats d'obs [hors papier]. Penser à **convertir les snapshots du pool** et les références d'évaluation. Toute modification d'environnement (curriculum d'états, changement d'adversaires scriptés) → annealing 0→100 % avec revert sur baisse de TrueSkill.

### 2.13 Exploration : entropie, randomisation d'environnement, diversité
**(1)/(2).** Bonus d'entropie c·S[π] ajouté à la loss PPO (App. O.1). **0,01 = meilleur en début de training** ; plus bas : explore moins ; plus haut (0,1) : "beaucoup plus mauvais", actions trop aléatoires ; 0 en début de training n'est pas optimal mais n'empêche pas d'apprendre (App. O.1, Fig. 28 ; valeurs testées 0, 1e-4, 1e-3, 1e-2, 1e-1). Schedule 0,01 → 0,001 (Five et Rerun, Tab. 2, Fig. 7). Randomisation d'env (App. O.2) visant trois choses : séquences longues et précises difficiles à découvrir, minima locaux d'un env répétitif, robustesse. Leviers : état initial perturbé (niveau, XP, or, armure, vitesse, régénérations, stats) ; **santé de Roshan aléatoire entre 0 et max** pour rendre une tâche dure apprenable ; lineups de héros aléatoires ; builds d'items perturbés. Les assignations de lane (avec pénalité de reward) apportent peu (Fig. 30). Pool de héros : 80 héros → speedup ≈0,8 (≈20 % plus lent) vs 17 (App. P, Fig. 31), d'où ≈20 % de temps en plus estimé.
**(3) RL-GCO.** Entropie 0,01 avec avantages normalisés, puis 0,003–0,001 en fin de training [hors papier pour les valeurs intermédiaires]. Repère : entropie max d'une table de 90 actions = ln 90 ≈ 4,50 nats [dérivé]. **Levier n°1 compatible GCO : la distribution d'états initiaux** (state setters RLGym), l'analogue direct de la santé de Roshan aléatoire. Balle près du but adverse ou avec vitesse vers le but, voitures placées au hasard, boost aléatoire, situations défensives. Ça multiplie les événements "but" par échantillon **sans toucher à la récompense**. Annealer ensuite vers la distribution réelle (kickoffs, ~5 min de jeu) avec la logique 0→100 % de l'App. B, et garder par exemple ≥30–50 % de kickoffs pour coller au déploiement RLBot [hors papier]. Diversité = adversaires passés + positions initiales variées ; pas besoin de varier les voitures au départ (Octane seul) [hors papier].

### 2.14 Stabilité : causes, détection, remèdes
**Causes documentées.**
- Données périmées (épisodes complets) → gradients inutiles/destructeurs (§4.4) ; staleness ≥ ~8 versions → ralentissement significatif (Fig. 5b).
- Sample reuse élevé (reuse ≈6,3 plafonne <75 TS, Fig. 24).
- Init aléatoire de nouveaux paramètres : du bruit envahit le modèle, gros gradients qui détruisent les comportements appris (App. B).
- Changement brutal d'env/action (Buyback) → chute de niveau (App. B).
- Nouvelles actions jamais explorées (App. F.1).
- Variance de récompense accrue (Divine Rapier, qui tombe à la mort) → valeur non fiable, boucle négative de reward et de TrueSkill dans Rerun ; résolu en bannissant l'item (App. Q.3). Dépendance au chemin : Five n'avait pas eu le problème car Rapier était arrivé après team spirit = 1 (Q.3).
- Réglage manuel frénétique des hyperparamètres avant TI 2018 (2 défaites), surnommé en interne "designing skyscrapers" (App. Q.1, Fig. 32).
- Run à 5 héros sous-performant sur les 4k premières versions, attribué à "une instabilité", non investigué (App. P).
**Détection.** TrueSkill continu (≈ toutes les 2 h, App. J) ; revert si le TrueSkill baisse pendant un anneal (App. B) ; métriques staleness et sample reuse mesurées en continu (§4.4, Fig. 23, 25) ; suivi reward épisodique et TrueSkill (Q.3).
**Remèdes.** Clip de gradient par paramètre (§3.2) ; LR = 0 après surgery (App. B) ; annealing des changements (App. B) ; staleness 0–1 et reuse ≈1 (§4.4) ; τ bas au début pour réduire la variance (App. G) ; 20 % d'adversaires passés (App. N) ; Rerun avec seulement **4 hyperparamètres** modifiés progressivement : LR, entropie, team spirit, horizon GAE (App. C) ; reverts.
**RL-GCO.** Tableau de bord minimal [hors papier] : TrueSkill/Elo vs pool fixe, buts marqués/encaissés par minute, entropie de la politique, KL approx., clip-fraction, explained variance de V, distribution de |avantage|, staleness, epochs/reuse, fréquences d'action par catégorie (flip, boost, jump). Règle Q.1 : **aucun changement manuel d'hyperparamètre hors schedule pré-écrit** ; changements progressifs, un à la fois, avec revert. GCO est structurellement à haute variance de retour (Q.3 montre qu'une variance accrue peut casser la valeur) → batch suffisant, critique séparé, horizon pas trop long au début.

### 2.15 Crédit à long horizon avec récompense sparse — synthèse
- Le papier ne propose **aucune** méthode spécifique au sparse au-delà de GAE + horizon long. Le shaping est son outil principal de crédit (App. G), et c'est précisément ce qui est interdit ici.
- Seules preuves : (a) crédit jusqu'à 6–12 min **pour un agent déjà compétent et shaped** (§4.5) ; (b) le win/loss pur avec H = 1 h atteint TS 155 > scripté, pour un coût en échantillons élevé et non chiffré (Fig. 16).
- Choix de segmentation : avec λ = 0,95, une fenêtre de 256 timesteps (≫ 1/(1−λ) = 20) "perd relativement peu" (§3.2). En RL, le segment par env doit être ≫ 1/(1−λ) ≈ 33 steps à λ = 0,97, soit ≥ 512 steps (≈34 s à 15 Hz, analogue des 256 steps Dota) [dérivé]. Bansal et al. calculent la GAE sur **rollouts complets** parce que la récompense de compétition est terminale et sparse (1710.03748 §4). En GCO, avec des épisodes coupés au but, ça revient à collecter des épisodes complets quand c'est possible.
- Leviers GCO concrets : horizon 10→30 s, λ ≈ 0,97, distribution d'états initiaux riche en buts annealée vers le réel, batch ajusté au noise scale, critique séparé, diagnostic de calibration de V (prédit-on bien qui marque ?).

## 4. Ce qui ne transfère pas (ou seulement sous condition)

1. **Shaping massif** (Tab. 6 : 20+ termes, win = 5 parmi eux), décroissance temporelle, pénalité de lane, zero-sum des termes shaped : **interdits par GCO**. Le papier lui-même qualifie ces signaux d'importants (§3.2), mais il n'a qu'une ablation sparse à petite échelle (Fig. 16).
2. **Le compute** : 150–820 PFlops/s·days d'optimisation, qui ne représentent que ≈30 % du coût (App. A). [dérivé] 150 PFlops/s·days ≈ 1,3·10²² FLOP. Rerun ≈ 1,7·10¹² timesteps : à 10k SPS (hypothèse laptop, à mesurer), il faudrait ≈ 5 ans. On joue donc dans une catégorie ≥ 3–4 ordres de grandeur en dessous.
3. **"Plus gros batch = mieux"** : vrai par itération et en wall-clock **avec du matériel parallèle en plus**. À débit fixe (laptop), 8× de batch pour 2,5× de speedup = ≈3,2× plus d'échantillons [dérivé]. Il faut choisir B ≈ ou < B_crit mesuré.
4. **Sample reuse ≈1** : mesuré à batch géant, buffer aléatoire et architecture asynchrone. En PPO synchrone à petite échelle, 2–3 epochs restent standard (PPO 1707.06347). À ablater, pas à copier.
5. **LSTM 4096 / 159 M params / BPTT** : justifiés par l'information partielle de Dota. RL 1v1 sous RLGym/RLBot est entièrement observé.
6. **Infra distribuée** (Redis controller, NCCL allreduce, 4 pools de machines, rollouts à 1/2 temps réel) : remplacée par une boucle locale synchrone ou double-buffer.
7. **LR 5e-5 → 5e-6** : calibré pour 159 M params et ~1M timesteps par step ; pas transposable tel quel.
8. **Surgery comme mode de vie** : motivée par 10 mois de patches Dota et de nouvelles mécaniques. Physique RL fixe → Rerun (20 % du coût, meilleur plafond) est la leçon pertinente.
9. **Team spirit, hero pool, scripts d'items/courier/ability builds** (App. F.1) : sans objet en 1v1 RL. Scripter des sous-systèmes (ex. kickoff) violerait l'esprit "PPO pur" : décision du studio.
10. **TrueSkill à 750 parties par version sur machines dédiées** : à réduire (100–300) avec des intervalles de confiance plus larges assumés.
11. **Réglages "équité humaine"** (réaction 167–267 ms, frameskip) : choix produit, pas des nécessités d'apprentissage.
12. **Auxiliaires win-probability qui rétropropagent dans le tronc** (App. D) : zone grise GCO (signal supervisé additionnel).
13. **Ce qui transfère bien** : PPO clip 0,2, λ ≈ 0,95 (à rescaler en temps), forme du schedule entropie 0,01 → 0,001 et LR ÷10 progressif, normalisation d'obs ±5, clip de gradient, 80/20 avec quality scores (η = 0,01), TrueSkill avec pool fixe et fenêtre ±10, staleness ≤1, ne changer que quelques hyperparamètres et progressivement, protocole de test d'horizon (Fig. 6), randomisation d'états pour rendre les tâches dures apprenables (Roshan, O.2), annealing 0→100 % des changements d'env (App. B), run from scratch propre une fois le design figé (Rerun).

Optima expérimentaux : cart-pole γ ∈ [0,96 ; 0,99], λ ∈ [0,92 ; 0,99] ; bipède 3D γ ∈ [0,99 ; 0,995], λ ∈ [0,96 ; 0,99] ; conclusion λ ∈ [0,9 ; 0,99].
- **An Empirical Model of Large-Batch Training — McCandlish et al., arXiv 1812.06162** (lu : abstract, §2.2–2.3, §3, §5, App. A.1, Tab. 1). B_simple = tr(Σ)/|G|² ; B_crit ≈ B_simple à l'ordre de grandeur ; compromis (S/S_min − 1)(E/E_min − 1) = 1 ; à B = B_crit on paie 2× le minimum de steps et 2× le minimum de données. Le noise scale et B_crit croissent fortement pendant le training (≥×10). Estimateur gratuit : normes de gradient "locale" vs "globale" + moyennes exponentielles (A.1). Tab. 1 (jeux, par observation) : Atari B_crit 100–1 000 (début) → 400–8 000 ; Dota 1v1 50 000 → 3 000 000 ; Dota 5v5 non mesuré, >8 000 000 (estimé) ; noise scale Dota 5v5 jusqu'à 24 000 000 (texte §3 : "au moins 10 millions"). La lecture de Tab. 1 vient d'une extraction PDF ; l'alignement des colonnes est à revérifier sur le PDF original.
- **Emergent Complexity via Multi-Agent Competition — Bansal et al., arXiv 1710.03748** (co-auteurs Pachocki, Sidor ; réf. [33]) (lu : §4.1, §4.2, §5.1, §5.3, §5.4). Récompense de compétition sparse ±1000 en fin d'épisode. GAE calculée sur **rollouts complets** car la récompense est terminale. Récompense d'exploration dense annealée à 0 (en 500 itérations, 1 000 pour kick-and-defend), soit ~10–15 % des epochs ; sans elle, les agents n'explorent pas le sparse (§5.3), **interdit en GCO**. Mais les agents entraînés jusqu'au sparse battent ceux qui gardent la dense (Fig. 3), argument pro-GCO une fois l'exploration amorcée. Adversaires tirés uniformément dans [δ·v, v] : le plus récent seul (δ = 1) est le pire ; δ = 0 meilleur pour Ant, δ = 0,5 pour Humanoid (Tab. 1, §5.4). PPO : Adam 1e-3, clip 0,2, γ 0,995, λ 0,95, 409 600 samples/itération, minibatch 5 120, 6 epochs (MLP) / 3 (LSTM), pas d'entropie (§5.1).
- **Open-ended Learning in Symmetric Zero-sum Games — Balduzzi et al., arXiv 1901.08106** (réf. [60] ; lu : abstract, intro). Un jeu fonctionnel = composante transitive + composante cyclique. Le self-play naïf peut cycler sans progresser dans les jeux non transitifs. PSRO_rN (rectified Nash response) construit des populations diverses. Pertinent pour justifier les 20 % d'adversaires passés et une éventuelle évaluation en population.
- **IMPALA — Espeholt et al., arXiv 1802.01561** (réf. [48] ; abstract seulement). Acteurs et learner découplés + correction off-policy V-trace, stable à haut débit. Piste si la staleness dépasse 1 un jour.

## 6. Expériences proposées pour le studio (directement tirées des protocoles du papier)

1. **Ablation horizon (protocole Fig. 6)** : depuis un checkpoint compétent, reprendre avec H ∈ {5, 10, 20, 40 s} pendant un nombre fixe d'itérations, mesurer le win-rate contre le checkpoint de départ (épisodes "premier but").
2. **Ablation reuse (protocole M.3)** : n_epochs ∈ {1, 2, 4}, métrique = wall-clock et échantillons pour atteindre un TrueSkill fixe vs pool de références.
3. **Noise scale (McCandlish A.1)** : logger B_simple toutes les N itérations ; augmenter le batch quand B_simple dépasse ~2× le batch courant [hors papier].
4. **Curriculum d'états (analogue Roshan + anneal App. B)** : part d'états "riches en buts" 80 % → 30 % ; revert si le TrueSkill baisse.
5. **Variance run-à-run (Fig. 20)** : 2–4 seeds courtes au départ pour connaître le bruit de la métrique avant de conclure sur une ablation (OpenAI : ≈2 TS).
